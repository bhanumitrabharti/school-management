Critical — Security

Critical Super Admin credentials are hardcoded plaintext in JS source
js/super-admin.js · Line 39

The line var CREDENTIALS = { username: 'superadmin', password: 'superadmin123' }; is shipped inside the publicly downloadable JS file. Anyone who opens browser DevTools → Sources can read these credentials without logging in. The Super Admin portal has full read/write access to all school tenants, all student data, and all fee records across every school.

There is no Firebase Authentication backing the Super Admin session — it is simply a sessionStorage.setItem('sa_session', 'active') flag set after string comparison. Clearing sessionStorage in the browser console, or setting it directly, gives Super Admin access with no credentials at all.

Affects Super Admin All School Admins All Teachers
Critical Dual-auth OR logic — Firebase failure does not block login
js/app.js · login() · ~Line 935 js/auth-utils.js

The login function runs two independent auth checks: Firebase signInWithEmailAndPassword and a custom credential check against Firestore data (AuthUtils.login). The success condition is if (firebaseResult && firebaseResult.user) || (customResult && customResult.success). Either one succeeding grants full login.

This means: if Firebase Auth is unreachable, misconfigured, or the Firebase Auth user does not exist, the custom check is the sole gatekeeper — and the custom check compares credentials against data stored in the same Firestore document the app already downloaded. The two systems are not redundant — they have different failure modes that together reduce security below either alone.

Affects School Admin Teacher Portal
Critical All access control is frontend-only — no server-side enforcement
js/app.js · renderSidebarNav() · navigate() Firestore Security Rules

Teacher access restrictions work by removing sidebar nav items and redirecting certain routes. The documented Firestore security rules require request.auth.token.role == 'super-admin' or a matching school_id claim — but neither custom teachers nor custom admins generate Firebase Auth tokens with these claims. The custom auth system (AuthUtils) never issues Firebase Auth credentials.

In practice, the Firestore rules cannot enforce role-based access. A teacher who opens the browser console and calls SchoolApp.store.fees.push({...}); SchoolApp.save() can write fee records. Nothing on the server blocks this.

Critical Teacher passwords stored inside the main tenant data document
Firestore: tenant_data/{schoolId}.teachers[].password js/auth-utils.js · hashPassword()

All teacher passwords live in the teachers array inside tenant_data/{schoolId} — the same document that holds every student name, parent phone number, attendance record, and fee transaction. The admin credential (adminPassword) is also in the same document under settings.

Bcrypt migration is implemented and partially correct, but: any admin who reads the Firestore document sees the password field for all teachers. More importantly, old plain-text passwords are only migrated at login time — teachers who haven't logged in since the feature was added still have plain-text passwords sitting in production data.

High — Data Architecture & Reliability

High Entire school data in one Firestore document — 1 MB hard limit will be hit
Firestore: tenant_data/{schoolId} js/app.js · save() · ~Line 272

Every piece of school data — students, teachers, attendance records, all fee transactions, all marks, notices, timetable — is stored in a single Firestore document per school. Firestore's hard document size limit is 1 MB. The code already warns about this at 900 KB with a toast message.

Shishu Vikash Mandir has 289 students. The auto-fee engine adds at minimum 289 fee records per month. After 12 months that is 3,468+ fee records, plus attendance, marks, and every other array. At current growth, this document will exceed the limit within one to two academic years, after which no save operation will succeed and the school will lose write access to their entire ERP.

Affects School Admin Teacher Portal
High Two independent auto-fee engines exist — risk of double-charging students
js/app.js · runAutoFeeReconciliation() js/fees.js · checkAndRunAutoCharge()

There are two entirely separate auto-fee systems. runAutoFeeReconciliation() in app.js runs on every page load and generates tuition dues for all missed months. checkAndRunAutoCharge() in fees.js runs when fees.js initializes and generates charges based on a separate autoChargeEnabled setting and autoChargeLastRun key.

These two systems use different trigger keys, different guard conditions, and different fee amounts. If both fire in the same month, a student receives two sets of dues. There is no deduplication check between them.

Affects School Admin
High Restore points are stored in localStorage — not a real backup
js/app.js · createRestorePoint() localStorage key: shishuvikash_restore_points

The "System Restore Point" feature stores snapshots in browser localStorage, limited to 5 points. localStorage is browser-specific, device-specific, and routinely cleared by browsers in private/incognito mode, when users clear site data, or when storage pressure is high. If the admin logs in from a different browser or device — or even the same browser after a history clear — all restore points are gone.

The auto-fee engine calls createRestorePoint() before bulk operations, so users are given the impression that their data is backed up before a major change. It is not. If the fee engine misfires, recovery is not possible from these points on any device other than the one that created them.

Affects School Admin
High Firebase app initialized twice — one project, two initializeApp() calls
js/app.js · Line 13 js/super-admin.js · Line 19

Both app.js and super-admin.js call initializeApp(firebaseConfig) with the identical config object. The Firebase SDK throws a warning — and in some versions an error — when the default app is initialized more than once. The two files each create independent Firestore instances pointing at the same project, with no shared state between them.

This is currently contained because the two portals run in separate HTML pages. However, if any shared module ever imports from both, initialization will fail unless handled with getApps(). It also means the Firebase API key, project ID, and app ID are duplicated in two places, creating a maintenance risk.

Affects Super Admin School Admin
High getInitialStore() default data is SVM-specific — new tenants inherit Bhanu's email and SVM's name
js/app.js · getInitialStore() · store · Lines 86–142

The getInitialStore() function — used to initialize both the in-memory store and as the reset baseline — contains hardcoded SVM-specific values: schoolName: 'Shishu Vikash Mandir', email: 'bhanu.bharti@ctrlshifts.in', adminUsername: 'admin', adminPassword: 'admin123', and lastAutomatedFeeRun: '2026-04'.

When a new school is onboarded and their Firestore document is initialized from this baseline, they will start with SVM's name, Bhanu's personal email, default credentials of admin/admin123 (a known-weak credential), and a lastAutomatedFeeRun date in the past — which will immediately trigger the auto-fee catchup engine and generate months of backdated dues on their first login.

Medium — Data Consistency & Architecture

Medium Fee data has two sources of truth with different key formats
store.feeHeads store.settings.feeHeads store.feeStructures store.settings.feeStructure

Fee heads exist at both store.feeHeads and store.settings.feeHeads. Fee structures exist at both store.feeStructures (keyed as fh_tuition) and store.settings.feeStructure (keyed as tuition, stripping the fh_ prefix). A migration block in load() tries to keep these in sync, but it runs silently on every load and maps different key formats.

The auto-fee engine reads from settings.feeStructure[class].tuition first, then falls back to feeStructures[class].fh_tuition. Any inconsistency between these two stores results in wrong fee amounts being charged without any visible error to the admin.

Affects School Admin
Medium Student name exists in two schemas — migration runs silently on every load
js/students.js · migrateStudentNames()

Student records have both a name field (full name) and firstName + lastName fields. The migrateStudentNames() function runs on every module load to derive one from the other. If derivation produces a different split than the original data — for example, "Rani Laxmi Bai" splits firstName="Rani", lastName="Laxmi Bai" — the migration overwrites the existing fields and silently calls SchoolApp.save().

There is no canonical field declaration in the schema. New students added from the admission form may use firstName+lastName; imported Excel students may use name. Different modules read different fields, creating inconsistency in search, attendance, and report cards.

Affects School Admin Teacher Portal
Medium SA Recovery Center is disconnected from tenant deletes
Firestore: sa_data/recovery_trash Firestore: tenant_data/{schoolId}.trash

There are two completely separate trash systems. When a tenant admin deletes a student or teacher, the record goes to tenant_data/{schoolId}.trash. The Super Admin Recovery Center reads from a separate sa_data/recovery_trash document. These two stores are never synchronized — a tenant delete does not write to the SA trash collection.

The SA Recovery Center currently shows only the seeded demo data (defaultRecoveryTrash) that was auto-initialized when the collection was first created. The Super Admin cannot actually restore deleted records from real schools using this interface.

Affects Super Admin School Admin
Medium Super Admin default seed data auto-creates fake schools in Firestore
js/super-admin.js · ensureDataLoaded() · Line 139–144

Inside ensureDataLoaded(), if the schools Firestore collection comes back empty, the code immediately auto-seeds it with defaultSchools — which includes "DAV Public School (Ranchi)" and "DPS Dhanbad" as fully-formed school records with IDs, subdomains, and contact details.

These are not demo records that stay local — they are written to the production Firestore via setDoc. Any future school directory listing, billing report, or data export will include these ghost schools unless they are manually deleted. The same pattern applies to sa_data/recovery_trash and sa_data/audit_logs.

Affects Super Admin
Medium assertSchoolIsolation() is defined but never called to block any operation
js/app.js · assertSchoolIsolation() · Line 148

The function assertSchoolIsolation(data, schoolId) exists and correctly checks whether data items belong to the active school. However, it is never invoked before any read or write. It returns a boolean but no caller acts on that boolean to block data operations. Multi-tenant isolation in data reads and writes is not enforced — it relies solely on the Firestore document structure (one document per school) and the currentSchoolId variable set in memory.

Low — Scalability & Performance

Low save() sends the entire store on every change — no delta writes
js/app.js · save() · Line 244

Every call to save() does a deep clone of the entire store and calls setDoc(docRef, payload, { merge: true }) with all data. Adding a single student, marking attendance, or updating a notice all result in the full 100KB+ document being serialized and written. The only exception is saveMarks(), which correctly uses a targeted updateDoc with a field path.

As the document grows toward the 1 MB limit, this pattern will become progressively slower and more bandwidth-intensive. The correct pattern — using targeted updateDoc with specific field paths — is already demonstrated in saveMarks() and should be the template for all saves.

Affects School Admin Teacher Portal
Low onSnapshot triggers full module re-render for most pages
js/app.js · load() · onSnapshot callback · ~Line 581

The Firestore onSnapshot listener fires whenever the tenant document changes. For the active page, this calls self.modules[self.currentPage].render() — a full re-render of the module. Only the exams page has throttling logic (5-second debounce). All other pages re-render completely on every snapshot event.

In a multi-user school where teachers are simultaneously marking attendance and the admin is viewing the fee ledger, this means the fee ledger re-renders every few seconds. With the full-document save pattern above, every write also triggers an onSnapshot, causing a render loop. This will cause visible flicker and UI state loss (open modals, partially-filled forms) for concurrent users.
